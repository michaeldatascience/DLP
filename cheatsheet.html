The big picture all four weeks are one pipeline

The whole course in one lineText becomes numbers, numbers go through a transformer, the transformer guesses the next token, and the guess is corrected. Weeks 1–4 are the four parts of that sentence.
WEEK 1Datasetload, map, filter the raw text
WEEK 2Tokenizer"the cat sat" → [9, 3, 8, 2]
WEEK 3Embedding lookupids pick rows of E → X (T × d)
WEEK 3Transformer blocksattention + FFN, L times
WEEK 3LM head + lossscores for all V tokens; loss = −ln p(next)
WEEK 4Adaptfine-tune, LoRA, or just prompt
  • The tokenizer is trained first, once, on the corpus (often a sample of it). You set the target vocabulary size V (for example 32,000) and the algorithm stops merging or pruning when it reaches it. The corpus decides which tokens; you decide how many. The vocabulary is then frozen. (If you reuse a pretrained model, V is whatever its tokenizer came with.)
  • The whole corpus is tokenized into one long stream of ids and cut into blocks of the context length.
  • Pre-training is one loop repeated millions of times: predict the next token, measure the loss, backpropagate, update. The answer key is the text itself, so no labels are needed.
  • The embedding table E starts random and is learned like any other weight. X is just rows looked up from E.
  • An untrained model's loss is about ln(V), because it spreads probability evenly over V tokens.

Who learns what

PartLearned howWhenSize
Tokenizercounting on the corpus. No gradients.once, before the modelV tokens

Position embeddingsbackprop from the lossmodel trainingcontext × d
Blocks (attention + FFN)backprop from the lossmodel training12d² each

  • The tokenizer and the embedding table are two different things. The tokenizer decides the V tokens. The embedding table gives each of those V tokens a vector of d numbers, starting random and improved by training.
  • The training loop, repeated millions of times: take a block of tokens → look up vectors → run the blocks → score all V tokens → loss → backprop → the optimizer updates every weight.

Week 2 · Tokenization about a quarter of the marks

The ideaA tokenizer turns text into integers and back. It is learned from the corpus before the model is trained. The three algorithms build the same kind of vocabulary and differ in one thing: the rule for choosing what to merge or drop.
The pipeline, always in this order

Normalizer → PreTokenizer → Model → PostProcessor  (and a Decoder to go back to text).

Remember it as Clean, Cut, Merge, Wrap: lowercase and tidy the text, split on whitespace, apply BPE / WordPiece / Unigram, add the special tokens.

WordMeaning
tokenThe unit the tokenizer produces. Can be a word, a piece of a word, or a character. Not the same as a word.
vocabulary, VThe fixed list of tokens, each with an id.
subwordA piece smaller than a word: “enjoyed” → “enjoy” + “ed”.
OOV / [UNK]A word not in V. Subword tokenizers avoid it by falling back to smaller pieces.
agglutinative languageBuilds long words by gluing pieces (Tamil, Turkish). Word-level vocabularies fail on it.

The lecture's worked example, in four lines

  • Corpus: “knowing the name of something is different from knowing something. knowing something about everything isn't bad” — 13 distinct words, starting vocabulary 22 symbols.
  • BPE: (i,n) and (n,g) both occur 7 times. (i,n) is met first, so it merges first → in. Next merge: (in,g) → ing.
  • WordPiece: score(t,h) = 5 / (8×5) = 0.125; score(a,d) = 1 / (3×2) = 0.167. The rarer pair scores higher even with a smaller count.
  • Unigram: p(k·now·ing) = 63/4096, p(know·ing) = 336/4096, p(knowing) = 768/4096. Fewer pieces usually wins. Viterbi on “whereby” gives where | by at −8.21 + −7.34 = −15.55.
What gets asked
  • Vocabulary size: larger V → shorter sequences but a bigger embedding table (V × d). Never both better.
  • For a fixed text, token count never goes up as V grows. It can stay flat.
  • Merge rules come from corpus statistics, not from meaning or morphology.
  • Text shattering into fragments, or many [UNK]s: retrain the tokenizer on in-domain text, or move from word-level to BPE / SentencePiece. Dropout, batch size or context length cannot fix it.

Padding, truncation, special tokens
  • padding=True pads to the longest sequence in the batch. padding="max_length" pads to a fixed length.
  • truncation=True cuts at the token limit. Without it nothing is cut, even past 512.
  • Special tokens are counted inside max_length.
  • BERT: [CLS] [SEP] [PAD] [MASK] [UNK] — five. A single sentence gets [CLS] … [SEP].
  • GPT-2: only <|endoftext|>, and no pad token until you set tokenizer.pad_token = tokenizer.eos_token.
  • Special tokens and their ids are model-specific.
From GA2 and GA3

  • Adding a frequent token by hand (FY) reduced the count, 25 → 22.

Solved · 2026 T2 Q18 · 4 marks

Batch ["Hi", "Hello beautiful world"] through a BERT tokenizer with padding=True. How many zeros in the first attention mask?

“Hi” → [CLS] hi [SEP] = 3 tokens. The other → [CLS] hello beautiful world [SEP] = 5 tokens. Pad the first to 5: mask = 1 1 1 0 0. Answer: 2.

The tokenizer only records where the padding is. Attention happens later, in the model.

Week 3 · Language models and GPT parameters, masks, architectures

The ideaA transformer block has two parts: attention, where tokens look at each other, and a feed-forward network, where each token is processed on its own. Stack L blocks, train it to predict the next token, and you have GPT.
SymbolMeaning
Vvocabulary size: how many tokens the tokenizer knows. You choose it before tokenizer training and it is frozen before the model is trained. It does not grow while the model trains.
d (d_model)length of the vector for one token — one number you choose
Thow many tokens this one input has after tokenizing, special tokens included. “the cat sat” → T = 4. In BERT, “Hi” → [CLS] hi [SEP] → T = 3. It changes with every input.
context lengththe fixed upper limit on T, set when the model is built (GPT-1: 512). The position table has exactly this many rows, so there is no row for token 513. T can be smaller, never larger.
L, hnumber of blocks, number of attention heads
N (“7B”)the count of all learnable numbers in the model. Not the same as d.
Where the parameters are
embeddings = V×d + context×d   |   attention = 4d²   |   FFN = 8d²   |   one block = 12d²
  • Why two tables? The first, V×d, has one row per vocabulary token: which token is this. The second, context×d, has one row per position: where in the input is it. A token's input vector is its token row plus its position row, added number by number. Without positions, “dog bites man” and “man bites dog” look the same to attention. Think of a name tag plus a seat number.
  • Cue in a question: “learned positional embeddings” means include context×d. If the question gives no position table, use V×d alone.
  • Attention has four d×d matrices: Q, K, V, O.
  • The FFN goes d → 4d → d: two matrices of d×4d. It is twice the size of attention.
  • Heads add no parameters. Two heads means splitting the columns of Q, K, V into two halves.
  • Sequence length adds no parameters. It only costs compute and activation memory.
  • A longer context adds only Δcontext × d (the position table). Tiny.
  • Check: GPT-1 = 40,478×768 + 512×768 + 12 × 12×768² = 116.4M.

Attention and the causal mask

  • Scores = Q Kᵀ / √d. This T×T matrix is the only O(N²) part of a transformer.
  • The causal mask puts −∞ where a token must not look. After softmax those become 0.
  • The blocked cells are strictly above the diagonal (“strictly upper triangular”). A token may see itself and the past.
  • Correct code: torch.triu(torch.ones(n,n), diagonal=1).
The mask bug · 2026 T2 Q9 · 3 marks

diagonal=0 also blocks the diagonal, so each token cannot see itself. The first row is all −∞ and softmax gives NaN. No error is raised.

CLM statements · 2026 T1 Q16
  • True — the loss at position t depends only on tokens before t.
  • True — the mask is strictly upper triangular.
  • True — the sequence probability is a product of next-token probabilities.
  • False — future tokens send gradients to earlier positions. The mask cut that path.

Week 4 · Adapting a pretrained model the biggest block of marks

The ideaA pretrained model knows language but not your task. You adapt it by changing weights (fine-tuning) or by writing a prompt. Changing weights costs memory, and most of week 4 is about where that memory goes and how to reduce it.

Ways to adapt

TypeDataWhat is learned
Task-specific fine-tuninglabelled data for one taskone task, usually through a new head
Continued pre-trainingunlabelled text from your domainthe domain's language. Same objective as pre-training.
Instruction tuninginstruction → response pairsto follow instructions
Preference tuninghuman choices between responseswhat people prefer (RLHF, DPO)
Promptingnone — no weights changezero-shot, few-shot (in-context), chain of thought
Graded False in GA4

“The training objective for continued pre-training and instruction tuning is the same.” False. Continued pre-training learns from every token of plain text. Instruction tuning learns to produce the response to an instruction.

Typical order with lots of raw domain text and a few instruction pairs: continued pre-training first, then instruction tuning.

Where the memory goes

The four copies
training = weights + gradients + momentum + variance = 4 copies × 4 bytes = 16 bytes per parameter
  • Momentum and variance are AdamW's two “optimizer states”.
  • Inference keeps only the weights: 4 bytes per parameter in fp32.
  • Weights alone: fp32 = 4 bytes, fp16 / bf16 = 2, int8 = 1, int4 = 0.5.
  • Activations are separate. They grow with batch size and sequence length, not with model size. Exam questions say “ignore activations”.

Always false
  • “FP16 halves the optimizer state.” No. The 32-bit master copy and both moments are kept.
  • “Gradient accumulation reduces the number of optimizer states.” No.
  • “The optimizer updates after every batch.” No. With gradient_accumulation_steps=8, once every 8 batches.
  • “Warmup reduces VRAM.” No. It only ramps the learning rate.
  • “Increasing vocabulary size helps with out-of-memory.” No. It makes the model bigger.
LoRA in five lines
  • Keep W frozen. Learn A (d×r) and B (r×d). Use W + A·B.
  • Trainable parameters for one matrix = 2·d·r. Raising the rank r raises this.
  • One of A, B starts at zero so the model starts unchanged.
  • The frozen base is still in memory. Only quantization shrinks it — hence QLoRA.
  • Head-only is the same idea in one place: a new last layer of d × num_labels parameters.
TrainingArgumentsMeaning
per_device_train_batch_sizesamples per batch on one GPU

From GA4 — 7B model, context 2048, d = 2048, 1,000,000 samples, batch 16, accumulation 4
  • Update steps in one epoch: 1,000,000 / (16×4) = 15,625.
  • “Weights update only at the end of an epoch” — False.
  • Memory to load in fp32: 7B × 4 = 28 GB. With context raised to 8000: still about 28 GB.
  • Classification head for 8 labels, no bias: 2048 × 8 = 16,384.
  • Head-only takes far less memory than full fine-tuning — True.
  • Raising LoRA rank r increases trainable parameters — True.
Solved · 2026 T1 Q8 · 2 marks

4B parameters, fp32, AdamW, one 32 GB GPU. Why is full fine-tuning impossible?

Weights 16 GB + gradients 16 GB + optimizer states 32 GB = 64 GB, which is more than 32 GB.

Numbers planted to mislead
  • Number of heads in a parameter question. Ignore it.
  • Sequence length (“only 3 tokens”) in a parameter question. Ignore it.
