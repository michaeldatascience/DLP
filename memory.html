DA5013 · Concept 04 · Week 4

The Memory Ledger

Training holds four copies of your model, not one. Once you can name the four, every memory question in week 4 becomes arithmetic, and every technique in the syllabus becomes a line item that strikes one of them out. This is the single largest block of marks on the paper.

01

Four copies, four bytes each

A parameter is one learnable number. To run a model you need the number itself. To train it you also need somewhere to accumulate its error, and AdamW keeps two running averages besides. Four numbers per parameter, four bytes each in fp32.

Copy 1 · always

The weights

4 bytes × N

The model itself. This is the only copy inference needs, which is why running a model costs a quarter of training it.

Copy 2 · training only

The gradients

4 bytes × N

One number per parameter saying which way to move it. Created by the backward pass, discarded after the step.

Copy 3 · AdamW

Momentum

4 bytes × N

A running average of recent gradients, so the update keeps rolling in a consistent direction instead of lurching with each batch.

Copy 4 · AdamW

Variance

4 bytes × N

A running average of squared gradients, letting each parameter get its own step size. Together with momentum these are the "optimizer states".

The sentence that answers every memory question Four copies, four bytes each, so sixteen bytes a parameter. A billion parameters costs 16 GB to train and 4 GB to load. The course defines 1 GB as 10⁹ bytes, so you never convert anything — just multiply and move the decimal point.
An analogy worth keeping Think of moving house. The weights are your furniture. The gradients are the note on each item saying which room it goes to. Momentum is your memory of which way you have been carrying things, and variance is your sense of which items are fragile and need small, careful moves. Only the furniture has to exist for you to live in the house — the other three are the apparatus of moving it, and you can put them down once you have arrived.

The three statements that are always wrong

"FP16 automatically reduces optimizer state size by half." It does not. Mixed precision keeps a full fp32 master copy of the weights and the optimizer moments, because repeatedly adding tiny updates to a 16-bit number loses them to rounding. That master copy is the entire point. What fp16 halves is activations and gradient storage, not optimizer state.

"Gradient accumulation reduces the number of optimizer states." It does not. The optimizer still keeps two numbers per parameter no matter how many forward passes you sum before stepping. Accumulation changes when you step, never what you store.

"Optimizer updates occur after every batch." With gradient_accumulation_steps = 8 they occur after every eight. That is the definition.

Memory hook for the levers Shrink, Skip, Forget, Freeze. Quantization shrinks each number. Accumulation skips the update until later. Checkpointing forgets activations and recomputes them. LoRA freezes the base so no gradients are owed on it. Four verbs, four different victims — and mixed precision is the odd one out, which is exactly why it is the one the exam lies about.

Now solve the real questions

2026 T1 · Q8 · 2 marks

A model with 4B parameters (fp32) is being trained using the AdamW optimizer on a single 32 GB GPU. Why is full fine-tuning impossible in this configuration?

1
Weights: 4e9 × 4 bytes = 16 GB.
2
Gradients: another 16 GB.
3
Optimizer: momentum 16 + variance 16 = 32 GB.
4
Total 64 GB against a 32 GB card. Set the panel to 4B, fp32, AdamW, V100 and the verdict bar turns red at exactly this figure.
5
The distractor to reject says fp32 means 8 bytes per parameter. It means 4. The other says the 4B parameters alone fill the card — they take 16 GB, which fits comfortably; it is the other three copies that break it.
optimizer 32 + weights 16 + gradients 16 = 64 GB > 32 GB
2026 T1 · Q18 · 4 marks · and 2026 T2 · Q17 · 4 marks

(a) A transformer has 1.2 billion parameters, fine-tuned with AdamW. Parameters, gradients and optimizer states (first and second moments) are all stored in 32-bit precision, 4 bytes each. Ignoring activations and buffers, calculate the total GPU memory in GB. (b) A model contains 5 billion parameters, trained with AdamW in fp32, same assumptions. Total memory in GB?

1
The question lists the four copies for you: parameters, gradients, first moment, second moment. Four copies at 4 bytes = 16 bytes per parameter.
2
(a) 1.2e9 × 16 = 19.2e9 bytes. With 1 GB = 10⁹, that is 19.2 GB. Accepted band 19.1 to 19.3.
3
(b) 5e9 × 16 = 80e9 → 80 GB. Accepted band 79.5 to 80.5.
4
No conversion, no powers of two. Multiply by 16 and shift the decimal point.
N × 16 bytes · 1.2B → 19.2 GB · 5B → 80 GB
2026 T2 · Q6 · 2 marks · and GA4

A 7 billion parameter model is loaded in FP32 precision. Ignoring activations and optimizer states, approximately how much GPU memory is required for storing model weights? And GA4's follow-up: if the context length rises from 2048 to 8000, how much is required then?

1
"Ignoring optimizer states" means only copy one is charged. 7e9 × 4 = 28e9 → 28 GB.
2
Tick Inference only on the panel with 7B and fp32 selected to see the other three copies vanish.
3
For the context change: longer context only adds rows to the positional embedding table, Δ = (8000 − 2048) × 2048 ≈ 12.2M parameters.
4
12.2M × 4 bytes ≈ 0.05 GB, on a model already weighing 28 GB. The answer stays 28 GB, and GA4's accepted band of 26 to 30 was deliberately wide enough that the increase cannot move you out of it.
28 GB, and still 28 GB after the context change
2026 T1 · Q13 and 2026 T2 · Q10 · 3 marks each · multiple select

Given TrainingArguments(per_device_train_batch_size=1, gradient_accumulation_steps=8, fp16=True, max_grad_norm=1.0), which effects are expected? And in T2's variant with fp16=True, gradient_accumulation_steps=8, per_device_train_batch_size=2, which statements are correct?

1
Effective batch size = per-device batch × accumulation steps. 1×8 = 8, and 2×8 = 16. Both papers asked you to confirm it exceeds the per-device figure. Correct.
2
fp16 reduces memory against fp32 training, via activations and gradient storage. Correct.
3
max_grad_norm=1.0 is gradient clipping: it caps the update size so one freak batch cannot wreck the weights. Correct.
4
"Gradient accumulation reduces the number of optimizer states." False. Two states per parameter regardless.
5
"Optimizer updates occur after every batch." False. After every eight.
6
"FP16 automatically reduces optimizer state size by half." False. The fp32 master copy is retained on purpose.
Effective batch grows · memory falls · clipping limits updates · accumulation can simulate larger batches. Everything about optimizer-state size is false.
2026 T2 · Q12 · 3 marks · and 2026 T1 · Q11 · 2 marks

(a) A team hits GPU out-of-memory errors while fine-tuning a language model. Which actions may help: mixed precision, quantization, gradient checkpointing, LoRA, increasing vocabulary size? (b) Which single technique is most effective at reducing GPU memory during training without modifying the model architecture: gradient clipping, mixed-precision training, increasing learning-rate warmup, or saving checkpoints less often?

1
(a) The first four each attack a real line in the ledger — activations, weights, activations again, and gradients-plus-optimizer. All four help.
2
Increasing vocabulary size makes the embedding table larger. It is the only option that moves memory the wrong way, and it is attractive because the other four are all "advanced technique" words.
3
(b) Gradient clipping bounds the gradient's magnitude, not its storage — the tensor is the same size either way. Warmup is a learning-rate schedule and saves nothing. Checkpoint frequency is disk, not VRAM.
4
Only mixed precision touches GPU memory at all, and it does so without changing a single layer.
(a) all but increasing vocabulary size  ·  (b) mixed-precision training
GA4 · Week 4 · the three you should re-derive

A 7B model, context 2048, embedding dimension 2048, dataset of 1,000,000 samples each exactly one context long, per-device batch 16, gradient accumulation 4. (a) How many optimizer update steps complete one epoch on a single GPU? (b) Fine-tuning for NER with 8 labels, tuning only the classification head — how many parameters in that head, excluding bias? (c) Does raising LoRA's rank r increase the number of tunable parameters?

1
(a) One update consumes an effective batch of 16 × 4 = 64 samples. 1,000,000 ÷ 64 = 15,625 steps.
2
The companion True/False — "the weight update happens only at the end of one epoch" — is false, and these 15,625 steps are the proof.
3
(b) The head maps the d-dimensional output vector to one score per label: 2048 × 8 = 16,384. The question says to exclude the bias, which would have added 8.
4
(c) True. LoRA replaces a d×d update with two matrices of shape d×r and r×d, so the trainable count is about 2dr per adapted matrix — linear in r. Rank is the dial that trades capacity against memory.
15,625 steps · 16,384 head parameters · rank up means parameters up
