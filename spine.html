01

Dataset

import datasets
The job of this stage Take text that lives in a hundred different file formats and sizes, and turn it into one uniform object you can slice, transform and stream — without ever loading the whole thing into memory.

Terms

The behaviour this week is actually examined on Every transform writes a new cache file rather than editing the old one. So disk usage grows with each .map(), and adding one sizeable column can roughly double the space the dataset occupies. Both of those were True/False questions in GA1. The reason is that Arrow files are immutable once written — which is also exactly why memory-mapping is safe.
What to expect in the quiz Both past Quiz-1 papers contained zero questions on this module, because the graded-assignment style here ("download this and report the count") cannot be asked in a closed-book exam. What can be asked is the conceptual shape above: what each method does, and how caching behaves. Budget about forty minutes on this stage, no more.
02

Tokenizer

import tokenizers / AutoTokenizer
The job of this stage Convert text into a list of integers the model can look up, and convert the model's integers back into text. Nothing else in the pipeline sees words.

The four-step pipeline, always in this order

StepComponentWhat happensExample
CleannormalizerLowercase, strip accents, collapse repeated spaces, remove HTML."Hmm.., I Don't" → "hmm.., i don't"
Cutpre_tokenizerFirst rough split, usually on whitespace. This is what used to be called "tokenization" before subwords existed.→ [hmm.., i, don't]
MergemodelThe learned algorithm — BPE, WordPiece or Unigram — breaks each piece into subwords from the vocabulary.→ [hmm.., i, do, ##n't]
Wrappost_processorInsert the model's own special tokens around the sequence.→ [CLS] hmm.., i do ##n't [SEP]
Memory hook Clean, Cut, Merge, Wrap. Four verbs, and they map one-to-one onto the four settable properties of the Tokenizer class. If you can say the four verbs you can name the four components.

Terms

The three algorithms — only the merge rule really differs

AlgorithmDirectionWhat it merges or dropsUsed by
BPEgrowsMerges the pair with the highest raw count. Greedy and deterministic.GPT-2, GPT-1
WordPiecegrowsMerges the pair with the highest score = count(a,b) ÷ (count(a) × count(b)). Dividing by the parts favours pairs whose halves are individually rare, so common letters do not dominate.BERT
Unigram
(SentencePiece)		shrinksStarts from a deliberately oversized vocabulary and repeatedly deletes the subwords whose removal costs the least likelihood. Picks a segmentation by probability, using Viterbi search, rather than by replaying merges.T5, ALBERT, XLNet
Memory hook Two build up from characters, one carves down from a big block. BPE and WordPiece are sculptors adding clay; Unigram is a sculptor removing marble. And within the two that grow: BPE counts, WordPiece scores.
The vocabulary-size trade-off, which is asked constantly A larger vocabulary means each word needs fewer tokens, so sequences get shorter — but the embedding table is V × d, so it gets bigger. You are trading sequence length against parameter count. Any option claiming a larger vocabulary reduces both, or reduces total compute outright, is wrong. GA2 added the real-world wrinkle: past a point, raising V stops shortening the sequence at all, because the extra merges are for words your text does not contain.

The parameter count assembles cleanly — check it yourself Embeddings 40,478×768 + 512×768 = 31.3M. Attention per block 4d² = 2.36M. FFN per block 8d² = 4.7M. So 12d² ≈ 7.1M per block, times 12 blocks = 85M. Total 31.3 + 85 ≈ 116M. Say "attention is four, feed-forward is eight, twelve per block" and you can rebuild any transformer's size from scratch.
04

Adaptation

transformers + peft + trl + bitsandbytes
The job of this stage Take the general-purpose pre-trained model and make it do your task — either by changing its weights, or by changing nothing and just writing a better prompt.

The branching tree — everything in week 4 sits on one of these two limbs

Weights changeWeights do not change
name fine-tuning prompting
when training time; needs gradients, so needs the memory for them inference time; no gradients, so far less memory
variants full fine-tuning · head-only · PEFT (LoRA, QLoRA, AdaLoRA) · continued pre-training · instruction tuning · preference tuning (RLHF, DPO, IPO, KTO) zero-shot · few-shot, also called in-context learning · chain of thought · prompt chaining · meta prompting
cost a separate copy of the model per task one model serves every task, reachable by API

Terms

Continued pre-training is not instruction tuning — you got this one wrong in GA4 They feel alike because both continue training an already-trained model on text, so it is tempting to call the objective the same. The grader says otherwise. Continued pre-training predicts every token of plain domain text with no labels at all. Instruction tuning trains on explicit instruction-and-response pairs, where the point is learning to obey a request, and the loss is concentrated on the response. One teaches the model a subject; the other teaches it a manner. A full side-by-side of all four adaptation types is the first thing I'll put in the Notes.
The memory story that nearly every week-4 question reduces to Training holds four copies of the model: the weights, their gradients, and Adam's two running averages (momentum and variance). Four copies × four bytes each = 16 bytes per parameter. Inference holds only the first of the four, which is why it needs a quarter of the memory. Every memory lever in the course just attacks one of those four copies, or the activations alongside them.
05

The seven numbers

≈ 30% of the paper
Why these seven Every numeric short-answer question across both past Quiz-1 papers and all four graded assignments reduces to one of these. Learn the story, not the symbols — the symbols follow from the story.
1 · Memory to train
bytes = N × 16 (fp32 + AdamW)
You are carrying four copies of the model — weights, gradients, momentum, variance — and each number is four bytes. Four fours are sixteen.
1.2B → 19.2 GB  ·  5B → 80 GB  ·  4B → 64 GB, which is why it will not fit on a 32 GB card
2 · Memory to merely load
bytes = N × 4 (fp32) · N × 2 (fp16) · N × 1 (int8)
Only the first of the four copies. Drop the question's mention of optimizer states and you are just weighing the weights.
7B fp32 → 28 GB  ·  7B int8 → 7 GB
3 · Embedding parameters
params = (V × d) + (ctx × d)
Two lookup tables, both d wide. One row per vocabulary entry, plus one row per position in the context. Only counts the second term when the model learns its positional embeddings — sinusoidal ones are free.
V=32000, ctx=2048, d=1024 → 34.9M  ·  V=65000, ctx=4096, d=1536 → 106.1M
4 · Parameters inside one block
attention = 4d² · FFN = 8d² · block = 12d²
Attention has four square matrices — query, key, value, output. The feed-forward goes d → 4d → d, which is two matrices of d × 4d, so eight. Heads and sequence length do not appear, and past papers plant both as decoys.
d=768 → attention 2.36M  ·  d=1536 → attention 9.44M
5 · Optimizer steps in one epoch
steps = samples ÷ (B × G × devices)
An update happens once per effective batch, not once per forward pass and certainly not once per epoch. So divide the pile by the size of one bite.
1,000,000 ÷ (16 × 4) → 15,625 steps
6 · Tokens processed in a run
tokens = B × G × ctx × steps
Effective batch size, times the tokens in each sample, times how many times you did it.
8 × 4 × 4096 × 10,000 → 1310.7M tokens
7 · Classification head
params = d × num_labels (+ num_labels if bias counted)
One weight from every dimension of the output vector to every possible label. Read whether the question says to exclude the bias — it usually does.
d=2048, 8 entity labels → 16,384
Bonus · Change from a longer context
Δparams = Δctx × d
Lengthening the context only adds rows to the positional table. It does not touch the vocabulary table, the attention matrices or the feed-forward layers — so the memory needed to load the model barely moves. GA4 built a whole question on people expecting otherwise.
512 → 1024 at d=768 → 0.393M  ·  2048 → 8000 at d=2048 → 12.2M, about 0.05 GB on a 28 GB model
06

Every abbreviation, in one place

If a short form appears anywhere in the course material and you cannot expand it instantly, it belongs here. Type to filter.

AdamW
The optimizer used throughout. Keeps two running averages per parameter, which is why training costs four copies of the model rather than two.
Arrow
The columnar on-disk format the datasets library stores everything in.
BPE
Byte Pair Encoding. Subword tokenizer that repeatedly merges the most frequent adjacent pair.
CLM
Causal Language Modelling. Predict the next token from the previous ones.
[CLS]
Classification token. Placed at the front of a BERT input; its output vector represents the whole sequence.
CoT
Chain of Thought. Prompting the model to write out intermediate reasoning before its answer.
DPO
Direct Preference Optimization. Preference tuning without training a separate reward model.
EM
Expectation-Maximization. The two-step procedure Unigram uses to settle its subword probabilities.
<|endoftext|>
GPT-2's single special token. Marks a document boundary, and gets reused as the padding token because GPT-2 defines none.
FFN
Feed-Forward Network. The d → 4d → d pair of linear layers in each transformer block.
FLAN
The paper that popularised instruction tuning by reformatting many existing datasets into instructions.
fp32 / fp16 / bf16
Floating-point formats at 32 and 16 bits. bf16 trades precision for a wider range than fp16, which makes it more stable to train in.
GELU
Gaussian Error Linear Unit. The smooth activation function GPT uses in place of ReLU.
GIL
Global Interpreter Lock. The Python limitation that stops one process fetching the next batch while training on the current one, which is why DataLoader uses worker processes.
HF
Hugging Face. The company and the hub hosting roughly 150k datasets and 350k models.
in-context learning
Another name for few-shot prompting. The model picks up the task from examples in the prompt, with no weight update.
LoRA
Low-Rank Adaptation. Freeze the big matrix, train two thin ones beside it.
[MASK]
The token BERT substitutes for a hidden word during masked language modelling.
MLM
Masked Language Modelling. Hide some tokens, predict them from both sides.
MMLU
A multiple-choice benchmark across many subjects, used to score a model's general knowledge.
NER
Named Entity Recognition. Labelling which spans of text are people, places or organisations.
OOV
Out Of Vocabulary. A word the tokenizer's vocabulary does not contain.
[PAD]
Filler token added so every sequence in a batch is the same length.
PEFT
Parameter-Efficient Fine-Tuning. The library, and the family of methods it implements.
pre-tokenization
The rough first split, usually on whitespace, that happens before the subword algorithm runs.
QLoRA
LoRA on top of a 4-bit quantized base model.
RLHF
Reinforcement Learning from Human Feedback. The original method for aligning a model with human preferences.
[SEP]
Separator token. Ends a BERT sequence and divides a pair of sentences.
SFT
Supervised Fine-Tuning. Training on labelled demonstrations, usually the first stage of an alignment pipeline.
SentencePiece
A tokenizer that treats raw text as a stream of characters including spaces, so it needs no whitespace splitting and works on languages that have none.
softmax
Turns a vector of raw scores into probabilities that sum to one.
T5
An encoder–decoder model that casts every task as text-in, text-out.
[UNK]
The token substituted for anything the vocabulary cannot represent.
Unsloth
A library that makes single-GPU fine-tuning roughly 2.5× faster. Used in the week-4 instruction-tuning notebook.
Viterbi
A search that finds the single highest-scoring path through a set of choices without testing every combination. Unigram uses it to pick how to split a word.
WordPiece
BERT's subword tokenizer. Merges by a score that divides the pair's count by its parts' counts.
-100
The label value cross-entropy ignores. Marks positions that must not contribute to the loss.
